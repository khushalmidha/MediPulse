# Owner non-root access — manual Console setup

**Completed by owner,5November2026:** `medipulse-deployer` Console/MFA setup and non-root CLI identity verified. Owner-added Free Tier read policy now works: account plan PAID/ACTIVE,140USD plan credits returned (not a claim of total credits across Billing offers); usage response has no T4g entry, so remaining trial quota is not directly verified. No root fallback or paid provisioning. The instructions below remain the setup reference, not a request to recreate the user or repeat MFA. Earlier automatic IAM creation was rejected before execution with "blocked by policy"; owner completed the supported Console flow instead. No long-lived access key was created by the assistant.

1. In your existing MFA-protected owner Console, open **IAM → Users → Create user**. Name your own user **medipulse-deployer**, with no custom IAM path. For the standard IAM Console, enable **Provide user access to the AWS Management Console**, choose an IAM user, and require a password change on first login. Set/store the temporary password privately. If creating the user without console access, use **Users → medipulse-deployer → Security credentials → Console sign-in → Enable console access**, then require the next-sign-in change. Create **no access keys**. Do not use a different person's existing user.
2. Attach the inline JSON from [iam-bootstrap-self-service.json](iam-bootstrap-self-service.json). It grants only the owner's password/virtual-MFA enrollment, not infrastructure administration. Do not attach AdministratorAccess or existing broad groups. Keep credential downloads, passwords and QR/OTP data out of this repository, OneDrive-shared artifacts and chat.
3. In a separate private browser window, use the IAM account sign-in URL shown by AWS and log in as **medipulse-deployer**. Change the initial password. In **Security credentials → Multi-factor authentication → Assign MFA device**, enroll your authenticator privately, using a device name starting **medipulse-deployer** to match the prepared policy. Sign out/in and verify that the MFA challenge succeeds. The owner performs this step; the assistant does not handle the seed/QR/OTP.
4. Only after MFA enrollment, the owner attaches AWS managed **SignInLocalDevelopmentAccess** and the reviewed [iam-readonly-planning.json](iam-readonly-planning.json) inline policy. The latter enables the initial metadata/pricing/credit/budget planning subset; it intentionally does not grant create/stop/delete, guest execution, production DB access or arbitrary IAM changes. The broader spending-audit helper may require additional explicitly reviewed read-only service permissions; any AccessDenied is a coverage gap, not a reason to add AdministratorAccess. If billing reads are denied, review the account's IAM billing-access setting in the owner Console or inspect costs there; do not bypass restrictions.
5. In PowerShell run:

   ```powershell
   aws login --profile medipulse-deployer --region ap-south-1
   aws sts get-caller-identity --profile medipulse-deployer --query 'ends_with(Arn, `:root`)' --output text
   python tools/aws-readiness.py --profile medipulse-deployer
   ```

   Authorize the browser as **medipulse-deployer**, using MFA, not the already-open root identity. The root check must return **False**; if True, stop and correct the browser login. The readiness helper reports only redacted identity/credit information; do not paste full credential/config caches into chat. No long-lived AWS key is required. These commands do not provision resources or grant deployment permissions.
6. After non-root login is confirmed, optionally log out the old temporary root profile with `aws logout --profile khushal`. Preserve the owner's root MFA/recovery access. Paid deployment still requires a costed scope, separate explicit approval and reviewed narrowly scoped provisioning permissions; successful read-only login is not deployment approval.

**Console experience caveat:** AWS documents that its newer AWS experience cannot create IAM users with console access. If that is the interface your account presents, use its supported team/federated-access flow, or an already-supported IAM Identity Center/role route, rather than API/password-policy workarounds. Do not create an Organization or alter account/credit plans simply to complete this guide. Report the interface limitation before making account-level changes.
