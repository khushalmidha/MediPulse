# MediPulse implementation plan after Astra review

Prepared 11 October 2026 from baseline `c42c3529`. Companion evidence: [ASTRA_REVIEW.md](ASTRA_REVIEW.md). This is a bounded repair/product plan, not a production database execution approval. Keep the existing stack and prior preservation/queue/ledger work. Deliver a convincing connected outpatient product before starting the P19 inpatient expansion.

## Product direction

Make the pitch follow one patient through a real visit: discover a doctor, reserve/check in, find the next room, complete consultation, collect a specimen, receive a released report, collect a partial prescription, and understand the remaining task. Every role should see the same encounter, with only the fields and actions it is permitted to see. Operational exceptions make this useful: a missing physical file, unacknowledged critical result, pending stock and overdue follow-up should each have an owner and a next action.

Use the existing warm neutral surfaces and deep teal accent as the default visual language, with tenant branding applied through the existing contrast-aware tokens. Rework the dashboard and assistant to match. Red indicates errors/urgent or destructive actions; amber pending work; green/teal completed work; blue informational links/status. Status must also have text/icon meaning. A display formatter removes repeated leading `Dr.` prefixes and adds one appropriate title without rewriting historical names.

## Seed and preservation safeguards

1. **Read-only plan first.** Seed command defaults to dry-run and requires an explicit target database and dataset version. Refuse ambiguous/default connections and refuse production execution without the reviewed explicit target/plan. Do not load deployment environment implicitly in test tools. Report aggregate counts, schema requirements and missing references without printing patient details or credentials.
2. **No destructive reset.** Never drop collections, truncate the database, reset wallets, bulk rewrite names or reuse the broad historical seed scripts without a separate audit. Existing P23 archives, valid appointments/tokens, family history, wallets, transfers and identifiers remain intact.
3. **Manifest each planned write.** Stable dataset-scoped keys distinguish inserts from existing originals. Store private target IDs, precondition fingerprints, intended changes and dependencies outside Git/OneDrive. Prefer insert-only fixtures. An essential reference update must preserve its full original BSON and have a conditional preimage check. Abort on unexpected existing keys, changed fingerprints or cross-tenant links.
4. **Use real invariants.** Create fixtures through the corrected domain services or a dedicated validated importer with equivalent transactional checks. Do not skip authentication/concurrency rules by inserting inconsistent “completed” documents. Seed operation IDs are stable and replay returns the same entities without duplicating appointments, charges, reports or stock movements.
5. **Suppress every external effect.** Disable mail, SMS, payment/AI providers and event delivery in the isolated environment; inspect outbox/Kafka/socket paths. A future production import must mark its synthetic events for server-enforced non-delivery before any writes, since existing workers may be live. No welcome, invite, reminder, review or receipt emails; no claim of delivered notifications.
6. **Rehearse preservation and recovery.** Backup/fingerprint the isolated starting state, dry-run, apply, replay, assert graph/stock/ledger/identity invariants, then recover. Recovery removes only unchanged records created by that manifest in dependency order and conditionally restores explicitly updated originals. Stop for review if a fixture has acquired external references or user edits; never delete those blindly. Confirm originals are BSON-identical afterward.
7. **Present the concrete production proposal, if needed.** Include exact target, counts/collections, insert/update distinction, preserved-record checks, reviewed schema/index operations, worker/event suppression, backup/recovery evidence and writer coordination. Ask for that final production execution authorization only once it is concrete and reviewable. The completed P23 authorization does not cover this proposal.

## Pitch and verification contract

Use a six-step demonstration: patient discovery/booking; reception arrival and real guidance; nursing handoff/vitals; clinician reviewed note and orders; lab/pharmacy exception and resolution; patient released packet and operational dashboard. Present historical synthetic volume only when its graph reconciles. Include one failure/recovery example, such as a disconnected provider with preserved clinician notes, so the claim is resilience demonstrated by behavior.

Run meaningful regression tests for each repaired boundary, then full existing isolated integration tests and selected browser journeys at the final candidate. Frontend unit tests must import real application logic; browser tests must exercise forms/routes and verify rendered data after mutation. Record current revision, commands, fixture scope, observed results and remaining limitations. Do not carry forward P20 “passed” claims just because a helper suite is green.

No production mutation, message delivery, DNS/provider activation or deployment is performed by this document. The immediate authorized next work is local R0/R1 repair and isolated regression coverage, alongside the display-only naming/color fixes as scope permits.
