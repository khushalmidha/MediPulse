# P06 durable workflows and calls

## Behavior

- Booking, check-in, clinical transitions, cancellation and demo refunds commit queue revisions and notification jobs with their Mongo transaction. A failed outbox write rolls back that transaction and uses the existing persisted booking recovery. SMTP/Kafka failure after commit cannot undo a booking/payment.
- Jobs have a unique identity, atomic lease, renewal, ownership fencing, exponential retry (2 seconds up to one hour), eight attempts, and visible failed state. Completed/skipped OTP jobs discard encrypted payloads; the worker also clears expired secret bodies. Secret payloads use authenticated AES-GCM derived from the server signing key and are excluded from default projections and operator output. Drain outstanding OTP jobs before rotating TOKEN_KEY; changing that key invalidates their ciphertext.
- SMTP delivery is at least once: a crash after provider acceptance but before acknowledgement can produce another email. Persisted job deduplication prevents normal request/replay duplicates; it cannot promise exactly once delivery from an SMTP server.
- Kafka clinical events are optional outbox deliveries when configured. Critical mail uses Mongo jobs directly. The analytics consumer no longer sends mail and drops legacy OTP events; analytics payloads have a small financial allowlist. Kafka outage reports degraded readiness but does not make the API unavailable while Mongo/Redis are healthy. Other financial analytics remain optional telemetry; PaymentNotification records remain persisted by P04.
- Review jobs transfer from the legacy Redis queue to Mongo before removal. Failed delivery stays queued. Completion enqueues its review job in the clinical transaction. Walk-in patients without a registered account receive staff queue hints, without invalid patient mail jobs.
- Booking/reset OTP responses say **queued** only after challenge and encrypted delivery job commit. Unconfigured/disabled delivery refuses OTP requests. Booking OTP guesses have a fixed expiry, five-attempt cap, and atomic one-time proof creation; proof redemption shares the booking transaction. Booking resend has a one-minute cooldown. Existing Redis booking OTP/proofs are intentionally invalid after rollout; request a new OTP.
- Default consultation duration is manual (`CONSULTATION_DURATION_MINUTES=0`). A configured 1–480 minute duration persists an online consultation deadline when it starts. In-person visits remain manual. The deadline/refund worker scans Mongo immediately at startup and each minute, so restarts recover due work. The 30-minute unstarted **online demo booking** refund deadline is persisted; hospital in-person reservations are excluded.
- Socket events are refresh hints. Authorized staff/patient/doctor endpoints return current Mongo snapshots and queue revisions; client guards reject older revisions/responses and prior contexts. Pages refresh on reconnect/visibility plus periodic polling. Clinical payloads remain private/minimal. Staff permission changes and expired/revoked sessions disconnect existing sockets; signing-in again establishes rooms using current permissions.
- One API instance is supported (`API_INSTANCES=1`). Runtime rejects an explicitly configured larger count. No Redis adapter was added because this checkout declares one API deployment. Configure and verify an adapter/presence policy before horizontal API scaling.
- The patient's doctor-ready email is also enqueued with the start transition and suppressed if the visit has ended or the job expires. Hospital website alerts read the authorized patient token snapshot, recovering missed calls and ignoring stale socket payloads.
- Losing a doctor connection does not complete the visit. Both participants rejoin after transport recovery, rebuild the peer connection and request ICE restart after connection failures. The doctor ends via the authorized REST transition; the patient leaves/rejoins locally. Camera failure can fall back to real microphone audio; denied microphone access shows an explicit retry action. Snapshot polling also recovers missed end events.
- `GET /appointment/:id/call-credentials` validates an online appointment participant/status and returns `Cache-Control: no-store`. Backend `TURN_URLS`, `TURN_SHARED_SECRET`, and 60–3600 second `TURN_CREDENTIAL_TTL_SECONDS` issue coturn REST credentials bound to participant and visit. No TURN secret remains in VITE configuration. Unconfigured relay produces a truthful call notice; STUN-only calls cannot reach all networks.

## Rollout preparation (not executed on deployment data)

Run from `backend` with an explicit intended DATABASE_URL, never by assuming the production .env. Finish P03/P04/P05 migrations first. Pause all API/consumer writers; save private database/Redis backups. Do not rebuild/deploy old consumers alongside the new API: the old consumer still sends appointment mail from Kafka and could duplicate outbox delivery.

1. Inspect additive indexes: `node scripts/initDurableSchema.js`.
2. Apply: `node scripts/initDurableSchema.js --apply --writers-paused --backup <new-private-schema-plan.json>`.
3. Inspect legacy refund deadlines: `node scripts/migrateVisitDeadlines.js`.
4. Apply: `node scripts/migrateVisitDeadlines.js --apply --writers-paused --backup <new-private-deadline-plan.json>`. Eligible existing paid online queued/refund-pending visits get created/paid time plus 30 minutes; overdue ones become eligible immediately. Existing active visits with no persisted deadline remain manual.
5. Review disabled mail/Kafka settings, manual/configured consultation policy and one-instance API setting. Supply actual coturn REST configuration on the backend only if that provider is already authorized/configured. Update frontend/API/consumer together; do not expose a Metered provider API key in frontend env. Rotate any formerly exposed provider credential separately.
6. Start the new API worker, confirm readiness, inspect job counts/failures. Due legacy Redis review jobs transfer gradually without deletion before confirmed Mongo enqueue. Reconcile any old Kafka mail backlog separately: the new analytics consumer deliberately does not convert old broker messages into new emails because prior send/ack history cannot establish which emails were already accepted. No replay or forced resend of deployment messages was performed here.

## Visibility and recovery

- `node scripts/outboxJobs.js` prints state/kind counts, oldest dates, and up to 50 failed IDs with sanitized failure code; it excludes addresses, body, patient payloads and OTPs.
- After fixing a provider, `node scripts/outboxJobs.js --retry --id <failed-job-id>` retries one failed job. Expired OTP jobs cannot be retried. Jobs with an expired lease recover automatically; do not clear the outbox collection or queued payment records.
- Schema rollback: `node scripts/initDurableSchema.js --rollback --writers-paused --backup <same-plan.json>` removes only added indexes, retaining documents/collections. Keep writers paused for a coordinated version rollback.
- Deadline rollback: `node scripts/migrateVisitDeadlines.js --rollback --writers-paused --backup <same-plan.json>` verifies status/revision/deadline have not changed before removing only backfilled fields. Changed visits require reviewed recovery; completed refunds are not reversed.
- If an apply stops midway, keep writers paused. Rerun dry-run/apply with a new private backup to finish the remaining eligible fields/indexes. The original full plan can then roll back those additions. If visit status/revision changed, use reviewed recovery instead of forcing a field rollback; completed refunds remain final.
- Existing active visit timers were never persisted, so their original deadline cannot be reconstructed reliably. Keeping those visits manual avoids silently applying a new forced-end policy to ongoing care.

## Verification boundaries

Integration checks use a generated local test database and synthetic identities. Browser checks use actual RTCPeerConnection media with Chromium fake devices, local synthetic signaling, and host ICE candidates. They verify both participants, disconnect/rejoin, permission errors and ending; they do not verify a real patient's devices, an activated TURN provider, cross-network NAT traversal, actual SMTP acceptance, deployment restart or production DNS/cookies.
